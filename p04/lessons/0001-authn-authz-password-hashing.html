P04 · Lesson 0001

Authentication vs. Authorization — and how to actually store a password

Two questions every protected endpoint silently answers. One distinction that decides whether a breach leaks your users' passwords. By the end of this lesson you will (a) say which question is which, and (b) write the bcrypt helper that goes into your P03 codebase's new users table.

The two questions

Every request that hits a protected route has to answer two questions, in order:

  1. Authentication (AuthN) — who are you? The caller presents a credential (a password at login, a JWT afterwards). A successful AuthN produces an identity. It says nothing about what you may do.
  2. Authorization (AuthZ) — are you allowed to do that? Given that identity, may it perform this action on this resource? AuthZ is impossible without a prior AuthN.

Mnemonic that will save you on interviews: 401 = "I don't know who you are" (AuthN failed). 403 = "I know who you are, and you can't do that" (AuthZ failed). Memorise the ordering — 401 always precedes 403 in a request's life.

The P04 spec mixes both on purpose. POST /login is pure AuthN. GET /me is AuthN + trivial AuthZ ("you may read your own profile"). DELETE /urls/<id> on someone else's URL is an AuthZ failure even though AuthN succeeded — that's the 403 case the spec calls outspec.

AuthN's first problem: how to store "hunter2"

A user registers with an email and a password. You have to write something to the users table. The wrong options, in declining terribleness:

  • Plaintext. A DB dump = every user's password logged in cleartext. Users reuse passwords, so you've now breached their email, bank, everything.
  • SHA-256 / MD5 of the password. Cryptographically fine but fast: an attacker GPU-cracks billions of these per second. Without a salt, identical passwords produce identical hashes — precomputed "rainbow tables" crack them instantly.
  • SHA-256 with a per-user salt. Fixes rainbow tables, still too fast — an attacker with the salts still brute-forces at GPU speed.

The correct answer for P04 is bcryptHale 2010OWASP. Three properties matter:

  1. Slow by design. bcrypt derives its key schedule from the Blowfish cipher with a configurable iteration count 2^cost. Cost 12 ≈ 4 096 rounds ≈ ~250 ms on a laptop. Slowing each attempt by 10 000× is the entire point.
  2. Per-user random salt built into the hash string. Two users with the same password get different hashes; the salt is stored in the hash, so you don't manage a separate column.
  3. Adaptive. When GPUs speed up in five years, you bump cost 12 → 14. Existing hashes encode their own cost and still verify cleanly; you re-hash on next login.

A bcrypt hash is one self-describing string:

$2b$12$KIXr5ICp3WS0xJY7nOh.9OXHm0Ve7T1q1qOlm1nRfNxmDpCZQqD5.
# └┬┘└┬┘└──────────────┘└──────────────────────────────────────┘
#  │  │       │                        hash (184 bits, Base64)
#  │  │       salt (16 bytes, Base64)
#  │  cost (2^12)
#  version (2b)

The whole string — version, cost, salt, hash — is what you store in the hashed_password column. To verify a login, pass the stored string and the user's typed password to bcrypt.verify; the function reads cost and salt from the stored string and re-runs the derivation.

Your win for this lesson

  
Add this to your P03 codebase. One new model, one new helper. Don't wire any endpoint yet — that's Lesson 0002.


  
# requirements.txt (add)
passlib[bcrypt]==1.7.4
bcrypt==4.2.0       # passlib 1.7.4 prints a runtime warning under bcrypt 4; pin both

# app/security.py
from passlib.context import CryptContext

# CryptContext lets you swap schemes later without rewriting callers.
# "deprecated=auto" means: if you add argon2 first in the schemes list,
# existing bcrypt hashes still verify, and re-hash on next successful login.
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(plain: str) -> str:
    return pwd_context.hash(plain)            # generates salt, applies cost

def verify_password(plain: str, hashed: str) -> bool:
    # Reads cost & salt from `hashed`; re-runs the derivation; constant-time.
    return pwd_context.verify(plain, hashed)



  
# app/models.py  (extends your P03 models)
import uuid
from sqlalchemy import Column, String, Boolean, DateTime, func
from sqlalchemy.dialects.postgresql import UUID
from .database import Base

class User(Base):
    __tablename__ = "users"
    id           = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    email        = Column(String(254), unique=True, nullable=False, index=True)
    hashed_password = Column(String(128), nullable=False)   # never "password"
    role         = Column(String(16), nullable=False, default="user")  # "user" | "admin"
    is_active    = Column(Boolean, nullable=False, default=True)
    created_at   = Column(DateTime(timezone=True), server_default=func.now())



  
Then an Alembic migration generating the users table, and a quick smoke-test from a Python shell:


  
from app.security import hash_password, verify_password
h = hash_password("correct horse battery staple")
print(h)                          # $2b$12$…  (note the cost 12 baked in)
print(verify_password("correct horse battery staple", h))   # True
print(verify_password("wrong", h))                          # False


  
Pass default bcrypt==4.x will throw a warning under passlib 1.7.4 (a version pin mismatch). Pin both as shown. This is a real, current papercut — passlib docs acknowledge it. You will see the warning; it is safe to silence with warnings.filterwarnings until passlib 1.7.5 ships.
