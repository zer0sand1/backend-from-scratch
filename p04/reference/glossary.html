Reference · P04 · Authentication & Authorization

Glossary

The vocabulary every P04 lesson assumes you already speak. Terms are introduced here once, then used consistently in lessons and in code. If a lesson uses an auth term, it must mean what this page defines it to mean.

Identities & the two questions

Authentication (AuthN)
Answering “who are you?” — establishing that the caller is a known principal. A successful AuthN produces an identity, not permissions.
Authorization (AuthZ)
Answering “are you allowed to do that?” — deciding whether an already-authenticated identity may take an action on a resource. AuthZ happens after AuthN.
Principal
The entity whose identity is authenticated — a user, a service, a device. In code, usually expressed as user_id.
Credential
Secret evidence presented to authenticate: a password, an API key, a signed token, a client certificate.

Passwords & hashing

Hash
A one-way function from password → fixed-length string. Cannot be reversed to the password. "hunter2" → a bcrypt hash like $2b$12$….
Salt
Random bytes generated per-password and mixed into the hash. Defeats precomputed rainbow tables; ensures two users with the same password get different hashes.
Work factor (cost)
The 2^N iteration count bcrypt uses. Standard in 2025 is 12 (≈ 4 096 rounds). Doubles cost of attack and login per increment.
Pepper
A server-wide secret XORed into every password before hashing, stored outside the database. Even disclosing the DB does not crack hashes. Out of scope for P04's first pass.
bcrypt
Adaptive password hash built on the Blowfish key schedule. Embeds the salt and cost in the hash string itself, e.g. $2b$12$<salt><hash>. Slow by design.
Argon2id
Modern memory-hard password hash (PHC winner). Preferred over bcrypt for new systems that can take a dependency. P04 uses bcrypt because passlib/FastAPI docs center on it.

Tokens

JWT (JSON Web Token, RFC 7519)
Three Base64url parts joined by .: header.payload.signature. Signed but not encrypted — anyone holding it can read it.
Header
JSON object with alg (e.g. HS256) and typ (JWT). Attackers can mutate alg — server must pin the algorithm, never trust the header.
Claims
The payload object — statements about the principal. Standard claims: iss (issuer), sub (subject = user id), aud (audience), exp (expires), nbf (not before), iat (issued at), jti (token id).
Access token
Short-lived JWT (P04: 15 min) sent on every protected request as Authorization: Bearer <jwt>. Stateless — server validates by signature alone.
Refresh token
Long-lived credential (P04: 7 days) used only to mint new access tokens at POST /refresh. Never sent to resource endpoints. Can be revoked server-side, unlike a stateless JWT.
Refresh token rotation
Each /refresh issues a new refresh token and invalidates the old one. Detects theft: if two clients present the same refresh token, one is an attacker.

Authorization models

RBAC (Role-Based Access Control)
Permissions attach to roles, roles attach to users. P04 has two roles: user and admin. Check user.role == "admin" in a dependency.
Ownership / ACL
Per-resource check beyond role: a short URL has a user_id foreign key; only the owner (or an admin) may PUT/DELETE it.
401 Unauthorized
AuthN failure — no identity, or identity not recognised. Used for missing/expired/invalid token.
403 Forbidden
AuthZ failure — identity is known, but is not allowed to do this thing. Used when User A hits User B's URL.

OAuth2 (RFC 6749)

Grant type
The mechanism by which a client obtains an access token. Four from RFC 6749: authorization code, implicit (deprecated), client credentials, resource owner password credentials (the one P04 uses).
Bearer token
Token type used purely by presenting it (RFC 6750). “Bearer” = whoever bears it may use it — so guard transport (HTTPS only).
OAuth2PasswordBearer
FastAPI dependency that extracts a username/password from the standard form and returns a token. P04 uses it for the /token endpoint shape only.
